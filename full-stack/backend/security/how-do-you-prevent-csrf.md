## 7. Common interview questions

#### How do you prevent CSRF?
- **The Engine Mechanism (Why it behaves this way):** CSRF prevention is multi-layered: (1) SameSite cookies — Lax or Strict attribute blocks cross-site cookie sending, (2) Anti-CSRF tokens — random tokens embedded in forms and validated on the server, (3) Custom headers — require headers like `X-Requested-With` that browsers won't send cross-origin, (4) Token-in-header auth — Bearer tokens in Authorization header are CSRF-immune, (5) Verify Origin/Referer headers — check that requests come from trusted origins.
- **The Unforgettable Mental Model:** The **Triple Lock System**. SameSite is the first lock (blocks cross-site cookies). Anti-CSRF tokens are the second lock (requires a secret key). Custom headers are the third lock (requires a specific request format). All three must be unlocked for the request to succeed.
- **The Trap**: Relying on a single defense. SameSite can have edge cases, tokens can be leaked, and custom headers can be bypassed in some browser configurations. Defense-in-depth is essential.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I prevent CSRF through multiple layers. SameSite cookies (Lax or Strict) block cross-site cookie sending as the first line of defense. Anti-CSRF tokens provide a secret that malicious sites can't access. Custom headers like X-Requested-With add another layer since browsers won't send them cross-origin. For APIs, I use Bearer tokens in the Authorization header, which are CSRF-immune. I also verify Origin/Referer headers as an additional check. Defense-in-depth ensures that if one layer fails, others still protect."

#### How do anti-CSRF tokens work?
- **The Engine Mechanism (Why it behaves this way):** The server generates a cryptographically random token, stores it in the user's session, and embeds it in forms or returns it as a header. When the form is submitted, the token is sent with the request. The server verifies the token matches the session token. A malicious site can't read the token due to the same-origin policy, so it can't include it in forged requests.
- **The Unforgettable Mental Model:** The **Secret Password**. Each form has a secret password (CSRF token) that only the legitimate site knows. When the form is submitted, the server checks the password. The malicious site can't know the password, so its forged forms fail.
- **The Trap**: Using predictable CSRF tokens (timestamps, sequential IDs). Predictable tokens can be guessed by attackers. CSRF tokens must be cryptographically random.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Anti-CSRF tokens are cryptographically random values generated by the server, stored in the session, and embedded in forms or returned as headers. When a request is made, the token is sent and verified against the session. A malicious site can't read the token due to the same-origin policy, so it can't forge requests. I use the double-submit cookie pattern for stateless APIs — the token is in both a cookie and a header, and the server verifies they match."

#### How does the double-submit cookie pattern work?
- **The Engine Mechanism (Why it behaves this way):** The server sets a CSRF token in a cookie (readable by JavaScript) and expects the same token in a custom header (e.g., `X-CSRF-Token`). The server verifies the cookie value matches the header value. A malicious site can't read the cookie from another origin (same-origin policy), so it can't set the matching header. This pattern is stateless — no server-side session storage is needed.
- **The Unforgettable Mental Model:** The **Matching Keys**. The server gives you two matching keys — one in your pocket (cookie), one in your hand (header). When you arrive, the guard checks that both keys match. The malicious site can only see your pocket from afar, so it can't provide the matching hand key.
- **The Trap**: Not binding the CSRF token to the user's identity. An attacker could obtain a valid CSRF token for their own account and use it in a cross-site request. Bind the token to the user's session or identity.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: The double-submit cookie pattern sets a CSRF token in a readable cookie and expects the same token in a custom header. The server verifies they match. It's stateless — no server-side storage needed. A malicious site can't read the cookie from another origin, so it can't set the matching header. I bind the token to the user's identity to prevent attackers from using their own valid token in cross-site requests. This pattern is ideal for stateless APIs."

#### How do custom headers prevent CSRF?
- **The Engine Mechanism (Why it behaves this way):** Browsers enforce CORS preflight for custom headers. A cross-site request with a custom header like `X-Requested-With` triggers a preflight OPTIONS request, which the server can reject. Even without CORS, browsers won't send custom headers in simple cross-site requests. This means a malicious site can't forge a request with the required custom header.
- **The Unforgettable Mental Model:** The **VIP Dress Code**. The API requires a specific dress code (custom header). The malicious site can't dress the victim in the right outfit (browser won't send custom headers cross-origin), so the bouncer (server) turns them away.
- **The Trap**: Using simple headers that don't trigger CORS preflight. `Content-Type: application/json` triggers preflight, but `Content-Type: application/x-www-form-urlencoded` doesn't. The header must be one that browsers block cross-origin.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Custom headers prevent CSRF because browsers won't send them in cross-origin requests without a CORS preflight. When an API requires a custom header like X-Requested-With or X-CSRF-Token, a malicious site can't forge the request. I combine custom headers with SameSite cookies and anti-CSRF tokens for defense-in-depth. The key is using headers that trigger CORS preflight or that browsers block cross-origin."

#### What would you monitor for CSRF prevention?
- **The Engine Mechanism (Why it behaves this way):** Monitor: CSRF token validation failure rates, SameSite cookie blocking rates, CORS preflight failure rates, custom header presence rates, and cross-origin request patterns. Alert on CSRF validation failures (indicates attacks or misconfiguration) and unusual cross-origin request patterns.
- **The Unforgettable Mental Model:** The **CSRF Prevention Monitor**. You're watching how many forged requests are being caught (validation failures), whether cookies are being blocked correctly (SameSite rates), and whether cross-origin requests are behaving normally.
- **The Trap**: Not monitoring CSRF token validation failures. These indicate either active CSRF attacks or legitimate requests failing due to misconfiguration.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I monitor CSRF prevention through token validation failure rates, SameSite cookie blocking rates, CORS preflight failures, custom header presence rates, and cross-origin request patterns. CSRF validation failures indicate either active attacks or misconfiguration — both need investigation. I also monitor for unusual cross-origin request patterns that might indicate CSRF probing. Alerting on validation failure spikes catches attacks early."

## 8. Active recall test

1. **How do you prevent CSRF?**
   - **Explanation:** SameSite cookies (Lax/Strict), anti-CSRF tokens, custom headers (X-Requested-With), Bearer tokens in Authorization header (CSRF-immune), and Origin/Referer header verification.
2. **How do anti-CSRF tokens work?**
   - **Explanation:** Server generates random token, stores in session, embeds in form. Request must include matching token. Malicious site can't read token (same-origin policy), so can't forge it.
3. **What is the double-submit cookie pattern?**
   - **Explanation:** CSRF token is set in a readable cookie and expected in a custom header. Server verifies cookie value matches header value. Stateless — no server-side storage needed.
4. **How do custom headers prevent CSRF?**
   - **Explanation:** Browsers won't send custom headers in cross-origin requests without CORS preflight. A malicious site can't forge a request with the required custom header.
5. **Why are Bearer tokens CSRF-immune?**
   - **Explanation:** Bearer tokens are sent in the Authorization header, which browsers don't auto-send cross-origin. A malicious site can't forge the Authorization header.
6. **Why must CSRF tokens be cryptographically random?**
   - **Explanation:** Predictable tokens (timestamps, sequential IDs) can be guessed by attackers. Cryptographic randomness ensures the token can't be predicted or forged.
7. **What should you monitor for CSRF prevention?**
   - **Explanation:** Token validation failures, SameSite blocking rates, CORS preflight failures, custom header presence rates, and cross-origin request patterns. Alert on validation failure spikes.
