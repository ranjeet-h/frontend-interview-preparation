# Alembic Migrations

## Detailed explanation

Alembic manages database schema changes for SQLAlchemy apps. In interviews, connect the framework feature to request lifecycle, validation, dependency management, database safety, testing, and production behavior.

## 1. One-line mental model

Alembic versions database schema.

## 2. Problem it solves

It keeps FastAPI applications predictable by making contracts, shared logic, validation, or runtime behavior explicit instead of scattering framework code across handlers.

## 3. Core idea

- Use Python type hints as API contracts.
- Keep route handlers thin and delegate business logic to services.
- Use dependencies for shared request-time behavior.
- Return explicit response models and status codes.
- Test behavior through HTTP calls and dependency overrides.

## 4. Visual / analogy

```txt
Request -> dependency resolution -> validation -> endpoint -> service/database -> response model -> response
```

## 5. Minimal example

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str

@app.post("/items")
def create_item(item: Item):
    return {"data": item}
```

## 6. Real-world example

A production FastAPI service uses routers per domain, Pydantic schemas for input/output, dependencies for auth and DB sessions, exception handlers for consistent errors, and tests with dependency overrides.

## 7. Common interview questions

#### What is Alembic and why use it with FastAPI?
- **The Engine Mechanism (Why it behaves this way):** Alembic is a database migration tool for SQLAlchemy. It tracks schema changes as versioned Python scripts (migrations) that can be applied (upgrade) or reverted (downgrade). When you modify SQLAlchemy models, you generate a migration: `alembic revision --autogenerate -m "add_items_table"`. Alembic compares your models to the current database schema and generates the SQL to reconcile them. Apply migrations: `alembic upgrade head`. This ensures the database schema evolves with your code in a controlled, versioned, and reversible way.
- **The Unforgettable Mental Model:** The **Time Machine**. Each migration is a time step — forward (upgrade) or backward (downgrade). You can travel to any point in the database's history by applying or reverting migrations in order.
- **The Trap**: Manually running ALTER TABLE statements instead of using migrations. Manual changes aren't versioned, can't be reversed, and aren't reproducible across environments.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Alembic versioned database schema changes for SQLAlchemy. When I modify models, I generate migrations with alembic revision --autogenerate. I apply them with alembic upgrade head. This ensures schema changes are versioned, reversible, and reproducible across all environments."

#### How do you set up Alembic with FastAPI?
- **The Engine Mechanism (Why it behaves this way):** Initialize Alembic: `alembic init alembic`. Configure `alembic.ini` with the database URL. Edit `alembic/env.py` to import your SQLAlchemy models and set `target_metadata = Base.metadata`. This allows `--autogenerate` to detect model changes. Create the first migration: `alembic revision --autogenerate -m "initial"`. Apply it: `alembic upgrade head`. In CI/CD, run migrations before deploying the app. For production, run migrations as a separate step before starting the new app version.
- **The Unforgettable Mental Model:** The **Blueprint System**. alembic.ini is the project settings, env.py is the architect who knows the building plans (models), and migrations are the construction orders. The architect compares the current building to the plans and writes orders for what needs to change.
- **The Trap**: Not setting target_metadata in env.py. Without it, --autogenerate can't detect model changes and generates empty migrations.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I initialize Alembic, configure the database URL in alembic.ini, and set target_metadata in env.py to my SQLAlchemy Base.metadata. This enables autogenerate to detect model changes. I run migrations as a separate CI/CD step before deploying the app."

#### How do you handle data migrations vs. schema migrations?
- **The Engine Mechanism (Why it behaves this way):** **Schema migrations** change the database structure (add columns, create tables). Generated by `--autogenerate`. **Data migrations** change the data within the existing structure (populate new columns, transform data). Written manually in the migration's `upgrade()` function using `op.execute()` or SQLAlchemy sessions. For data migrations, use `op.get_bind()` to get a connection: `conn = op.get_bind(); conn.execute(text("UPDATE items SET status = 'active'))`. Data migrations should be idempotent — safe to run multiple times.
- **The Unforgettable Mental Model:** The **House Renovation**. Schema migration is adding a new room (structure change). Data migration is repainting the walls and rearranging furniture (content change) within the existing structure.
- **The Trap**: Mixing schema and data changes in the same migration. If the data migration fails, the schema change is already applied, leaving the database in an inconsistent state. Separate them.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Schema migrations change structure — generated by --autogenerate. Data migrations change content — written manually with op.execute(). I keep them in separate migrations so schema changes can be applied even if data migrations fail. Data migrations should be idempotent."

#### How do you run migrations in production?
- **The Engine Mechanism (Why it behaves this way):** Run migrations as a separate step before deploying the new app version: `alembic upgrade head`. In CI/CD pipelines: (1) Build the new app image, (2) Run migrations against the production database, (3) Deploy the new app. Migrations should be backward-compatible — the old app version should still work with the new schema during the deployment window. For zero-downtime deployments: add columns (don't remove), make new columns nullable initially, deploy the app, then make columns required in a subsequent migration.
- **The Unforgettable Mental Model:** The **Bridge Replacement**. You build the new bridge (new schema) alongside the old one, then switch traffic (deploy app). You don't tear down the old bridge before the new one is ready.
- **The Trap**: Running migrations after deploying the app. The new app may expect columns that don't exist yet, causing crashes. Always run migrations before deploying.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I run migrations before deploying the new app version. Migrations should be backward-compatible — the old app works with the new schema during deployment. For zero-downtime: add columns first (nullable), deploy the app, then make columns required in a subsequent migration."

#### How do you handle migration conflicts in a team?
- **The Engine Mechanism (Why it behaves this way):** When multiple developers create migrations simultaneously, they may conflict (same revision parent). Resolve by: (1) **Merge migrations** — `alembic merge -m "merge heads"`, which creates a merge revision with multiple parents, (2) **Rebase** — regenerate migrations against the latest schema, (3) **Serial migration creation** — coordinate with the team to create migrations sequentially. Alembic tracks the migration chain via the `down_revision` field. Merge revisions are the safest approach — they preserve both migration histories.
- **The Unforgettable Mental Model:** The **Git Branch Merge**. Two developers create migrations on different branches. When they merge, Alembic creates a merge revision (like a git merge commit) that combines both histories.
- **The Trap**: Manually editing down_revision to fix conflicts. This can corrupt the migration chain. Use alembic merge for safe conflict resolution.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: When migrations conflict, I use alembic merge to create a merge revision that combines both histories. This is safer than manually editing down_revision. For large teams, I coordinate migration creation or use a serial approach to avoid conflicts."

#### How do you test database migrations?
- **The Engine Mechanism (Why it behaves this way):** Test migrations by: (1) **Upgrade/downgrade cycle** — apply migration, then downgrade, verify no errors, (2) **Data integrity** — verify data is correctly transformed after migration, (3) **Backward compatibility** — verify the old app version works with the new schema, (4) **Idempotency** — run the migration twice, verify no errors. Use a test database for migration tests. Test both upgrade and downgrade paths — downgrade is critical for rollback scenarios.
- **The Unforgettable Mental Model:** The **Rehearsal**. Before the actual performance (production migration), you rehearse — run through the full upgrade and downgrade on a test stage to verify everything works.
- **The Trap**: Only testing upgrade, not downgrade. If a deployment fails and you need to rollback, the downgrade must work. Always test both directions.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I test migrations by running the full upgrade/downgrade cycle on a test database. I verify data integrity after migration and backward compatibility with the old app version. I always test downgrade — it's critical for rollback scenarios if a deployment fails."

## 9. Mistakes / traps

- Putting business logic directly in route handlers.
- Mixing request schemas, database models, and response models.
- Forgetting cleanup for request-scoped dependencies.
- Blocking the event loop with sync I/O inside async routes.
- Returning raw internal errors to clients.
