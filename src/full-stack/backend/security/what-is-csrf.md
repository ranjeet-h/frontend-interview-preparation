## 7. Common interview questions

#### What is CSRF (Cross-Site Request Forgery)?
- **The Engine Mechanism (Why it behaves this way):** CSRF is an attack where a malicious website tricks a user's browser into making an authenticated request to a target site where the user is logged in. Because browsers automatically send cookies with requests, the target site receives the request with the user's auth cookie and processes it as if the user intended it. The attack exploits the trust the site has in the user's browser, not the trust the user has in the site.
- **The Unforgettable Mental Model:** The **Forged Signature**. An attacker forges your signature (cookie) on a money transfer form (malicious request). The bank (target site) processes it because the signature looks genuine — it doesn't know you didn't sign it.
- **The Trap:** Thinking CSRF only affects cookie-based auth. CSRF affects any authentication mechanism that the browser automatically sends, including cookies and HTTP authentication. Token-in-header approaches (Bearer tokens in Authorization header) are immune because browsers don't auto-send custom headers.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: CSRF is an attack where a malicious site tricks a user's browser into making an authenticated request to a target site. Because browsers automatically send cookies, the request includes the user's auth cookie and the target site processes it. CSRF exploits the trust the site has in the user's browser. It's prevented by SameSite cookies, anti-CSRF tokens, and requiring custom headers that browsers won't send cross-origin."

#### How does a CSRF attack work?
- **The Engine Mechanism (Why it behaves this way):** Attack flow: (1) User is logged into target site (bank.com) with an auth cookie, (2) User visits a malicious site (evil.com), (3) Evil.com contains a hidden form that auto-submits a POST request to bank.com/transfer, (4) The browser sends the request with bank.com's auth cookie, (5) Bank.com processes the transfer because the request is authenticated. The user never intended to make this request.
- **The Unforgettable Mental Model:** The **Puppet Strings**. The malicious site pulls the strings (auto-submits a form), and the user's browser (puppet) performs the action. The target site sees the puppet moving and assumes the puppeteer (user) intended it.
- **The Trap:** Thinking the user needs to click something for CSRF to work. Many CSRF attacks use auto-submitting forms or invisible images that trigger requests without any user interaction.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: A CSRF attack works by embedding a form or request on a malicious page that auto-submits to the target site. When the victim (who is logged into the target site) visits the malicious page, their browser sends the request with the target site's auth cookie. The target site processes it as an authenticated request. The attack can be completely invisible — auto-submitting forms, invisible images, or JavaScript fetch calls. The victim never intended to make the request."

#### How do anti-CSRF tokens work?
- **The Engine Mechanism (Why it behaves this way):** Anti-CSRF tokens are random, unpredictable values generated by the server and embedded in forms or returned as headers. The server stores the token in the user's session. When a form is submitted, the token is sent with the request, and the server verifies it matches the session token. A malicious site can't read the token (same-origin policy), so it can't include it in the forged request.
- **The Unforgettable Mental Model:** The **Secret Handshake**. The server teaches you a secret handshake (CSRF token) that only you know. When you make a request, you perform the handshake. The malicious site can't see the handshake, so it can't forge it.
- **The Trap:** Using predictable CSRF tokens (timestamps, sequential IDs). Predictable tokens can be guessed by attackers. CSRF tokens must be cryptographically random.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Anti-CSRF tokens are cryptographically random values generated by the server and embedded in forms or returned as headers. The server stores the token in the session. When a request is made, the token is sent and verified against the session. A malicious site can't read the token due to the same-origin policy, so it can't include it in forged requests. The token must be unpredictable — using timestamps or sequential IDs defeats the protection."

#### How does SameSite cookie attribute prevent CSRF?
- **The Engine Mechanism (Why it behaves this way):** SameSite=Lax blocks cookies from being sent with cross-site POST requests. When a malicious site tries to submit a form to the target site, the browser doesn't include the auth cookie. Without the cookie, the request is unauthenticated and fails. SameSite=Strict blocks all cross-site requests, including GET navigation.
- **The Unforgettable Mental Model:** The **Neighborhood Mail Rule**. SameSite=Lax says: "Don't deliver mail from outside the neighborhood for packages (POST)." The malicious site's package form submission doesn't get the auth cookie delivered, so the request fails.
- **The Trap:** Relying solely on SameSite=Lax for CSRF protection. Lax allows cross-site GET requests, so if your app performs state-changing operations via GET, SameSite won't protect them.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: SameSite=Lax prevents CSRF by blocking cookies from cross-site POST requests. When a malicious site tries to submit a form, the browser doesn't send the auth cookie, so the request is unauthenticated. SameSite=Strict is more secure but breaks cross-site navigation. For defense-in-depth, I use SameSite=Lax plus anti-CSRF tokens for state-changing operations. SameSite alone isn't sufficient if the app uses GET for mutations."

#### How do custom headers prevent CSRF?
- **The Engine Mechanism (Why it behaves this way):** Browsers enforce CORS preflight for custom headers (like `X-CSRF-Token` or `Authorization`). A cross-site request with a custom header triggers a preflight OPTIONS request, which the target server can reject. Even without CORS, browsers won't send custom headers in simple cross-site requests. This means a malicious site can't forge a request with the required custom header.
- **The Unforgettable Mental Model:** The **VIP Dress Code**. The club (API) requires a specific dress code (custom header). The malicious site can't dress the victim in the right outfit (browser won't send custom headers cross-origin), so the bouncer (server) turns them away.
- **The Trap:** Thinking any custom header prevents CSRF. The header must be one that triggers a CORS preflight or that browsers won't send cross-origin. Simple headers like `Content-Type: application/x-www-form-urlencoded` don't trigger preflight.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Custom headers prevent CSRF because browsers won't send them in cross-origin requests without a CORS preflight. When an API requires a custom header like `X-Requested-With` or `Authorization`, a malicious site can't forge the request because the browser blocks the header. This is why token-in-header approaches (Bearer tokens) are CSRF-immune — the browser doesn't auto-send the Authorization header cross-origin."

#### What would you monitor for CSRF?
- **The Engine Mechanism (Why it behaves this way):** Monitor: CSRF token validation failure rates, SameSite cookie blocking rates, CORS preflight failure rates, and cross-origin request patterns. Alert on CSRF validation failures (indicates attacks or misconfiguration) and unusual cross-origin request patterns.
- **The Unforgettable Mental Model:** The **CSRF Security Monitor**. You're watching how many forged requests are being caught (validation failures), whether cookies are being blocked correctly (SameSite rates), and whether cross-origin requests are behaving normally.
- **The Trap:** Not monitoring CSRF token validation failures. These indicate either active CSRF attacks or legitimate requests failing due to misconfiguration.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I monitor CSRF through token validation failure rates, SameSite cookie blocking rates, CORS preflight failures, and cross-origin request patterns. CSRF validation failures indicate either active attacks or misconfiguration — both need investigation. I also monitor for unusual cross-origin request patterns that might indicate CSRF probing. Alerting on validation failure spikes catches attacks early."

## 8. Active recall test

1. **What is CSRF?**
   - **Explanation:** Cross-Site Request Forgery — an attack where a malicious site tricks a user's browser into making an authenticated request to a target site. Exploits automatic cookie sending.
2. **How does a CSRF attack work?**
   - **Explanation:** Malicious site embeds an auto-submitting form targeting the victim's logged-in site. Browser sends the request with auth cookie. Target site processes it as authenticated.
3. **How do anti-CSRF tokens prevent CSRF?**
   - **Explanation:** Server generates random token, embeds in form, stores in session. Request must include matching token. Malicious site can't read the token (same-origin policy), so can't forge it.
4. **How does SameSite prevent CSRF?**
   - **Explanation:** SameSite=Lax blocks cookies from cross-site POST requests. Without the auth cookie, the forged request is unauthenticated and fails.
5. **How do custom headers prevent CSRF?**
   - **Explanation:** Browsers won't send custom headers in cross-origin requests without CORS preflight. A malicious site can't forge a request with the required custom header.
6. **Why are Bearer token APIs CSRF-immune?**
   - **Explanation:** Bearer tokens are sent in the Authorization header, which browsers don't auto-send cross-origin. A malicious site can't forge the Authorization header.
7. **What should you monitor for CSRF?**
   - **Explanation:** CSRF token validation failures, SameSite blocking rates, CORS preflight failures, and cross-origin request patterns. Alert on validation failure spikes.
