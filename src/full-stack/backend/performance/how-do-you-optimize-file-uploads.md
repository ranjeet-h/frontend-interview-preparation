## 7. Common interview questions

#### How do you optimize file uploads?
- **The Engine Mechanism (Why it behaves this way):** File upload optimization involves multiple strategies: direct-to-storage uploads (client uploads directly to S3/GCS, bypassing the server), multipart uploads (split large files into chunks for parallel upload and resume capability), presigned URLs (server generates temporary upload credentials, client uploads directly), chunked uploads (client splits file into chunks, server reassembles), compression before upload (reduce file size client-side), and validation before upload (check file type, size, and dimensions before transferring). The biggest optimization is bypassing the application server entirely.
- **The Unforgettable Mental Model:** The **Direct Delivery**. Instead of delivering a package to your office, having you repackage it, and then sending it to the warehouse (server-mediated upload), the delivery truck goes directly to the warehouse (direct-to-storage).
- **The Trap:** Routing file uploads through the application server. The server becomes a bottleneck — it must receive, process, and forward every byte, consuming memory, CPU, and bandwidth.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I optimize file uploads by using direct-to-storage uploads with presigned URLs. The server generates a temporary upload credential, and the client uploads directly to S3 or GCS, bypassing the application server entirely. For large files, I use multipart uploads with chunked transfer for parallel upload and resume capability. I also validate file type and size client-side before upload to reject invalid files early, and I compress files client-side when possible."

#### What are presigned URLs and how do they optimize uploads?
- **The Engine Mechanism (Why it behaves this way):** A presigned URL is a time-limited, permission-scoped URL generated by the server that allows direct upload to cloud storage (S3, GCS). The server authenticates the user, validates the upload request (file type, size), generates the presigned URL with specific permissions (PUT only, specific bucket/key, expiry time), and returns it to the client. The client uploads directly to storage using this URL. This bypasses the application server, reducing server load and enabling faster uploads (direct connection to storage's high-bandwidth infrastructure).
- **The Unforgettable Mental Model:** The **Hotel Key Card**. The front desk (server) verifies your identity, then gives you a key card (presigned URL) that opens only your room (specific bucket/key) and expires at checkout (expiry time). You go directly to your room without the front desk escorting you.
- **The Trap:** Generating presigned URLs without validation. If you don't validate file type and size before generating the URL, users can upload anything directly to your storage.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Presigned URLs are time-limited, permission-scoped URLs that allow direct upload to cloud storage. The server validates the request (file type, size, user permissions), generates a presigned URL with specific permissions and expiry, and returns it to the client. The client uploads directly to storage, bypassing the application server. This reduces server load and enables faster uploads. I always validate before generating the URL to prevent unauthorized uploads."

#### How do multipart uploads work?
- **The Engine Mechanism (Why it behaves this way):** Multipart uploads split large files into chunks (typically 5-100MB each), upload each chunk independently, and then combine them server-side. Benefits: parallel upload (multiple chunks simultaneously), resume capability (if one chunk fails, retry only that chunk), and memory efficiency (process chunks instead of the entire file). The process: initiate upload (get upload ID), upload chunks (each with a part number), complete upload (combine chunks), or abort upload (cancel and clean up). Cloud storage services (S3, GCS) support multipart uploads natively.
- **The Unforgettable Mental Model:** The **Puzzle Delivery**. Instead of shipping a completed 1000-piece puzzle (risk of damage, hard to handle), you ship it in boxes of 100 pieces each. If one box is damaged, you only resend that box. The recipient assembles the puzzle.
- **The Trap:** Not cleaning up aborted multipart uploads. Incomplete uploads leave orphaned chunks that consume storage. Implement lifecycle policies to auto-delete incomplete uploads after a period.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Multipart uploads split large files into chunks that are uploaded independently and combined server-side. This enables parallel uploads, resume capability (retry failed chunks), and memory efficiency. The process is: initiate (get upload ID), upload chunks (each with a part number), complete (combine), or abort (clean up). I use multipart uploads for files over 100MB and implement lifecycle policies to auto-delete incomplete uploads after 24 hours to prevent orphaned chunk storage."

#### How do you handle file upload validation?
- **The Engine Mechanism (Why it behaves this way):** Validation should happen at multiple layers: client-side (instant feedback, check file type, size, dimensions before upload), server-side before generating presigned URL (verify user permissions, file type whitelist, size limits), and post-upload (virus scanning, content verification, image dimension validation). Client-side validation improves UX but can be bypassed — always validate server-side. Use file magic numbers (not just extensions) for type verification, as extensions can be spoofed.
- **The Unforgettable Mental Model:** The **Airport Security**. Client-side is the check-in counter (basic checks, quick feedback). Server-side before upload is the security checkpoint (thorough verification). Post-upload is the customs inspection (final verification after arrival).
- **The Trap:** Relying only on file extensions. A file named "photo.jpg" could be an executable. Use magic numbers (file signature bytes) for actual type verification.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I validate uploads at multiple layers. Client-side for instant UX feedback — check file type, size, and dimensions before upload. Server-side before generating presigned URLs — verify permissions, file type whitelist (using magic numbers, not just extensions), and size limits. Post-upload — virus scanning, content verification, and image dimension validation. Client-side validation can be bypassed, so server-side validation is mandatory."

#### How do you handle failed file uploads?
- **The Engine Mechanism (Why it behaves this way):** Failed uploads require retry logic and state management. For direct-to-storage uploads: the client handles retries (exponential backoff, retry only failed chunks in multipart). For server-mediated uploads: the server should be idempotent (same upload request doesn't create duplicates), support resume (track uploaded chunks, resume from last successful chunk), and clean up partial uploads on failure or timeout. Implement upload session tracking — store upload state (initiated, in-progress, completed, failed) to enable resume and cleanup.
- **The Unforgettable Mental Model:** The **Save Point in a Game**. If you die (upload fails), you don't start from the beginning — you resume from the last save point (uploaded chunk). The game tracks your progress (upload session state).
- **The Trap:** Not cleaning up partial uploads. Failed uploads leave orphaned files or chunks that consume storage. Implement cleanup on failure and lifecycle policies for orphaned data.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I handle failed uploads with client-side retry logic using exponential backoff. For multipart uploads, only failed chunks are retried. I track upload session state (initiated, in-progress, completed, failed) to enable resume capability. On failure or timeout, I clean up partial uploads to prevent orphaned data. The server is idempotent — the same upload request doesn't create duplicates. I also implement lifecycle policies to auto-delete incomplete uploads after a period."

#### How do you optimize image uploads specifically?
- **The Engine Mechanism (Why it behaves this way):** Image upload optimization: client-side compression and resizing before upload (reduce file size), server-side processing pipeline (generate multiple sizes/thumbnails using ImageMagick, Sharp, or cloud services like Cloudinary), WebP/AVIF conversion (better compression than JPEG/PNG), and CDN delivery with automatic format negotiation (serve WebP to supporting browsers, JPEG as fallback). Store the original for reprocessing, and generate derivatives on-demand or during upload.
- **The Unforgettable Mental Model:** The **Photo Lab**. You bring a high-res photo (original upload). The lab creates prints in multiple sizes (thumbnails, medium, large), converts to efficient formats (WebP), and distributes them to galleries (CDN). The original is kept safe for future reprocessing.
- **The Trap:** Storing only the processed versions. If you need a new size or format later, you can't regenerate from a compressed derivative. Always store the original.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I optimize image uploads with client-side compression and resizing before upload to reduce transfer size. Server-side, I run a processing pipeline that generates multiple sizes and converts to WebP/AVIF for better compression. I store the original for future reprocessing and generate derivatives on-demand or during upload. The CDN serves the appropriate format based on browser support. This balances upload speed, storage efficiency, and delivery performance."

#### How do you handle concurrent file uploads?
- **The Engine Mechanism (Why it behaves this way):** Concurrent uploads require: upload limits per user (prevent resource exhaustion), queue management (process uploads in order or prioritize), storage bandwidth management (cloud storage has rate limits), and progress tracking (show progress for each concurrent upload). For direct-to-storage uploads, the client manages concurrency (browser limits concurrent connections per domain). For server-mediated uploads, use a job queue to process uploads asynchronously and avoid blocking web workers.
- **The Unforgettable Mental Model:** The **Highway Toll Lanes**. Multiple lanes (concurrent uploads) process cars faster, but too many lanes cause congestion at the exit (storage bandwidth). Toll booths (limits) control the flow.
- **The Trap:** Allowing unlimited concurrent uploads. A single user uploading 100 files simultaneously can exhaust storage bandwidth and block other users. Implement per-user concurrency limits.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I handle concurrent uploads with per-user concurrency limits to prevent resource exhaustion. For direct-to-storage uploads, the browser manages connection limits. For server-mediated uploads, I use a job queue to process uploads asynchronously. I track progress for each concurrent upload and provide feedback to the user. I also monitor storage bandwidth and implement backpressure when approaching rate limits."
