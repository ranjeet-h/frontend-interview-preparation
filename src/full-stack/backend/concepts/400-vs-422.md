# 400 vs 422

## Detailed explanation

400 means the request is malformed or cannot be parsed; 422 means the request is syntactically valid but semantically invalid for the domain.

## 1. One-line mental model

400 is broken request shape; 422 is valid shape with invalid meaning.

## 2. Problem it solves

Validation errors are easier for frontends when parsing errors and business validation errors are separated.

## 3. Core idea

- Use 400 for invalid JSON, missing content type, malformed query params.
- Use 422 for field validation failures after parsing succeeds.
- 422 often returns field-level error details.
- Some teams use 400 for all validation; consistency matters most.
- Document the project convention.

## 4. Visual / analogy

```txt
400 = unreadable form. 422 = readable form with wrong values.
```

## 5. Minimal example

```txt
return res.status(422).json({ errors: { email: "Invalid email" } });
```

## 6. Real-world example

Registration payload with malformed JSON returns 400; valid JSON with weak password returns 422.

## 7. Common interview questions

#### What is the difference between 400 and 422?
- **The Engine Mechanism (Why it behaves this way):** 400 Bad Request means the server cannot parse or understand the request — malformed JSON, missing Content-Type header, invalid query parameter syntax, or structurally broken data. 422 Unprocessable Entity means the request is syntactically valid and was parsed successfully, but the data fails semantic or business validation — valid JSON with an invalid email format, a password that's too short, or a date in the past for a future booking. The distinction is: 400 = "I can't read this," 422 = "I read it but it's wrong."
- **The Unforgettable Mental Model:** 400 is **a letter written in a language you don't understand**. 422 is **a letter in your language that makes no sense** — "Please send me the moon."
- **The Trap:** Using 400 for everything. Some teams use 400 for all validation errors, which is acceptable if documented consistently. The problem is mixing approaches — sometimes 400, sometimes 422 — which confuses clients.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: 400 means the request is malformed and cannot be parsed — invalid JSON, missing headers, or broken syntax. 422 means the request was parsed successfully but the data fails validation — valid JSON with an invalid email, a password too short, or a date range that doesn't make sense. The distinction is structural vs. semantic: 400 is 'I can't read this,' 422 is 'I read it but the values are invalid.' Some teams use 400 for all validation; the key is consistency."

#### Why does the 400 vs 422 distinction matter?
- **The Engine Mechanism (Why it behaves this way):** The distinction helps clients handle errors appropriately. A 400 error often means the request format is fundamentally broken — the client may need to fix the serialization, headers, or content type before retrying. A 422 error means the format is correct but the values need adjustment — the client can display field-level validation errors to the user. Frontend form libraries use 422 responses to map errors to specific input fields, while 400 responses typically trigger a generic "something went wrong" message.
- **The Unforgettable Mental Model:** 400 tells the developer **"fix your code."** 422 tells the user **"fix your input."**
- **The Trap:** Returning 422 for malformed JSON. If the body isn't valid JSON, the server can't even parse it to determine it's a validation error — it must be 400.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: The distinction helps clients respond appropriately. 400 errors indicate structural problems — the client may need to fix serialization or headers. 422 errors indicate validation problems — the client can display field-level errors to the user. Frontend form libraries map 422 response fields to specific inputs, while 400 responses typically trigger generic error messages. This separation lets the frontend provide targeted feedback for validation errors while handling structural errors at the transport level."

#### What bugs happen when 400 and 422 are confused?
- **The Engine Mechanism (Why it behaves this way):** Returning 400 for validation errors prevents the frontend from displaying field-level error messages — the form library expects 422 with a structured error body containing field paths. Returning 422 for malformed JSON is technically incorrect because the server couldn't parse the request to validate it. Inconsistent usage forces the frontend to parse error bodies for every 4xx response instead of routing by status code, making error handling fragile and endpoint-specific.
- **The Unforgettable Mental Model:** Confusing 400 and 422 is like **a teacher marking a test wrong for the wrong reason** — "you failed because you wrote in pencil" (400) vs. "you failed because your answer is incorrect" (422).
- **The Trap:** Returning 200 with validation errors in the body instead of 422. This is a common anti-pattern that breaks HTTP semantics and prevents automated error handling.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Confusing 400 and 422 breaks frontend error handling. If validation errors return 400, the form library can't distinguish them from structural errors and can't map field-level messages to inputs. If malformed JSON returns 422, it's semantically wrong — the server couldn't parse the request to validate it. The most common bug is returning 200 with validation errors in the body, which prevents HTTP libraries from routing to error handlers and breaks caching behavior."

#### How does a frontend client react differently to 400 vs 422?
- **The Engine Mechanism (Why it behaves this way):** On 400, the frontend typically shows a generic error message like "Invalid request format" because the error may be structural and not field-specific. On 422, the frontend parses the error body for field-level details and displays them next to the corresponding form inputs. React form libraries like React Hook Form have built-in handlers for 422 responses that map `{ "errors": { "email": "Invalid email" } }` to the email field's error state.
- **The Unforgettable Mental Model:** 400 = **show a general alert banner**. 422 = **highlight the specific form fields in red with error messages**.
- **The Trap:** Not having a fallback for 400 errors. If the frontend only handles 422 field errors, a 400 response shows nothing to the user because there are no field-level errors to display.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: On 400, the frontend shows a generic error message because the problem is structural — invalid JSON, missing headers — not field-specific. On 422, the frontend parses the error body for field-level validation errors and displays them next to the corresponding form inputs. Form libraries like React Hook Form have built-in support for mapping 422 error objects to field error states. The frontend should handle both: field-level display for 422, and a fallback banner for 400."

#### How would you test 400 and 422 behavior?
- **The Engine Mechanism (Why it behaves this way):** Testing 400 involves sending malformed requests: invalid JSON bodies, missing Content-Type headers, wrong data types (string instead of number), and structurally broken payloads. Testing 422 involves sending syntactically valid requests with invalid values: invalid email formats, passwords below minimum length, dates in the past, enum values outside allowed range. Integration tests verify that the validation layer correctly distinguishes between parse errors (400) and validation errors (422), and that the error body contains field-level details for 422 responses.
- **The Unforgettable Mental Model:** Testing 400/422 is like **testing a form with two types of bad input**: gibberish text (400) and valid-looking but wrong answers (422).
- **The Trap:** Only testing with valid payloads. The error paths are where most bugs live — missing validation for edge cases, inconsistent error shapes, and wrong status codes.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I test 400 by sending malformed requests — invalid JSON, missing Content-Type, wrong data types. I test 422 by sending valid JSON with invalid values — bad email formats, short passwords, out-of-range dates, invalid enums. I verify that 400 responses indicate structural problems and 422 responses include field-level error details. I also test boundary cases — empty strings, null values, maximum length strings — to ensure validation catches all invalid inputs with the correct status code."
