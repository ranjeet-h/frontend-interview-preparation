# 400 Bad Request vs 422 Unprocessable Entity: Syntactic vs Semantic Validation

## 1. Why This Exists — The Problem First

Imagine a user filling out a 20-field registration form on your web app. They hit submit. Instantly, a bright red banner appears at the top of the viewport: `"400 Bad Request: An error occurred."` 

No input fields turn red. No helper text appears beneath the email or password fields. The user has no idea whether their chosen username is taken, their password lacks a special character, their birthday is in the future, or their network connection dropped a packet and sent a truncated payload. They try clicking submit again, get the same opaque 400 error banner, and abandon the onboarding flow.

Behind the scenes, the frontend team is having a nightmare. Because the backend returns `400 Bad Request` for *every* client-side failure—from a corrupted JSON syntax error to a failed regex check on a phone number—the frontend client cannot distinguish between two fundamentally different categories of problems:
1. **Transport and syntax corruptions:** The request envelope is unreadable garbage that requires a generic error banner or an engineering telemetry alert.
2. **Actionable user input errors:** The request was received and parsed cleanly, but specific fields failed domain rules and need inline, field-level error messages attached to form inputs.

For public APIs, microservices, and mobile apps, this ambiguity creates even worse failures. Automated SDK clients and webhook consumers that receive a `400` assume the request framing itself is broken (e.g., corrupted encoding, invalid headers) and may refuse to retry, or conversely, spam retries because they have no programmatic way to know that the business domain rejected the logical state of the payload.

The root cause of this confusion is conflating **syntactic validity** (can the server parse the raw incoming bytes?) with **semantic validity** (does the parsed data make logical sense in our business domain?). HTTP gave us `400 Bad Request` in RFC 7231 for syntax and transport failures, while RFC 4918 (originating in WebDAV and universally adopted by modern REST frameworks) formalized `422 Unprocessable Entity` for semantic business rule violations.

## 2. The Analogy — Make It Obvious

Think of mailing a paper mortgage application to a bank:

```txt
┌─────────────────────────────────────────────────────────────────────────┐
│                           THE MAILROOM (Parser)                         │
│                                                                         │
│   Incoming Envelope ──> Is it legible English? ──No──> 400 BAD REQUEST  │
│                                │                                        │
│                               Yes                                       │
│                                ▼                                        │
│                      THE LOAN OFFICER (Domain)                          │
│                                │                                        │
│                 Do the financial numbers make sense?                    │
│                                │                                        │
│                       ┌────────┴────────┐                               │
│                      Yes                No                              │
│                       ▼                 ▼                               │
│                   200 / 201 OK    422 UNPROCESSABLE                     │
│                                   (With field notes)                    │
└─────────────────────────────────────────────────────────────────────────┘
```

- **Case 1: 400 Bad Request (Syntactic Failure)**  
  You send an envelope, but the paper inside is shredded into confetti, soaked in black ink, or written in an unreadable cipher. The mailroom clerk opens it and cannot even figure out what document this is, who sent it, or where the name field is supposed to be. The mailroom rejects it on the spot: *"This envelope is unreadable garbage. We cannot even parse what you sent."*

- **Case 2: 422 Unprocessable Entity (Semantic Failure)**  
  You send a crisp, perfectly legible application form. The mailroom opens it, reads every single section without issue, and hands it to the mortgage loan officer. The officer reads it line by line: your name is clear, but in "Date of Birth" you wrote "Next Friday", under "Requested Loan Amount" you wrote "-$100,000", and your "Employment Start Date" is dated after your "Employment End Date". The form is 100% syntactically perfect and completely readable, but logically nonsensical according to banking rules. The officer stamps it: *"I understood every word you wrote, but I cannot process this application because the data violates our rules."* They attach sticky notes to each invalid field detailing exactly what must be corrected.

## 3. How It Actually Works — The Full Explanation

Modern web architectures split request handling into a clear **Two-Tier Validation Pipeline**. Understanding where your validation logic runs determines whether an error is a 400 or a 422.

```txt
Incoming HTTP Request
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ TIER 1: Transport & Syntactic Parser                   │
│ • HTTP Framing & Header Validation                     │
│ • Content-Type Header Verification (application/json)  │
│ • Raw Byte Streaming & Character Decoding (UTF-8)      │
│ • JSON.parse() / Wire Deserialization                  │
└────────────────────────────────────────────────────────┘
       │
       ├──[ Parse Error / Malformed Syntax ]──> HTTP 400 BAD REQUEST
       │                                        {"title": "Invalid JSON syntax"}
       ▼
[ Successfully Deserialized Data Object ]
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ TIER 2: Semantic & Domain Validation                   │
│ • Schema Type Coercion & Constraints (Zod, Pydantic)   │
│ • Field Rules (regex, min/max length, email format)    │
│ • Relational Invariants (end_date > start_date)        │
│ • Business State Checks (insufficient funds, duplicate)│
└────────────────────────────────────────────────────────┘
       │
       ├──[ Domain Rule Violation ]────────────> HTTP 422 UNPROCESSABLE ENTITY
       │                                        {"errors": [{"field": "age", ...}]}
       ▼
[ Valid Domain Command ] ──> Execute Controller & DB Mutation ──> HTTP 200 / 201
```

### Tier 1: Syntactic & Transport Validation (`400 Bad Request`)

Tier 1 executes at the transport and serialization boundary, usually inside web server adapters or body-parsing middleware (e.g., `express.json()`, Starlette ASGI body reader, NGINX reverse proxy).

The server evaluates questions like:
- Is the HTTP framing intact, or is the `Content-Length` header mismatched with the actual byte stream?
- Is the `Content-Type` header valid and supported?
- Is the raw body string valid JSON? For example, did the client send `{"name": "Alice",}` (illegal trailing comma) or `{"query": undefined}` (unquoted invalid token)?
- Are the URL query parameters structurally broken (e.g., invalid percent-encoding like `?filter=%ZZ`)?

If any check fails at Tier 1, execution halts before your application controller or schema validator is ever called. The server cannot construct a structured in-memory object (a JavaScript object or Python dictionary). Because the server cannot even understand what the client is asking, it responds with **`400 Bad Request`**.

### Tier 2: Semantic & Domain Validation (`422 Unprocessable Entity`)

Tier 2 executes *after* the raw byte stream has been successfully parsed into an in-memory data structure. The payload is 100% syntactically valid JSON. 

Your application now evaluates domain and business invariants using schema libraries (such as Zod, Pydantic, Joi, or custom domain models):
- **Field Constraints:** `email: "user@"` (fails email regex), `password: "123"` (fails min-length rule), `age: -5` (integer is valid JSON, but negative age is physically impossible).
- **Cross-Field Invariants:** `booking_end: "2026-01-01"` occurs before `booking_start: "2026-01-10"`.
- **Domain State Conflicts:** Attempting to register an account when `username` is already taken, or requesting a transfer amount greater than the current balance.

The server completely understands the request envelope, the content type, and the parsed fields. However, the instructions contained within the payload cannot be processed by the business domain. The server responds with **`422 Unprocessable Entity`** and provides structured, field-level error messages.

### The RFC Standard: RFC 7807 (Problem Details for HTTP APIs)

Both 400 and 422 errors benefit enormously from standardized response payloads. The IETF formalized **RFC 7807 (Problem Details for HTTP APIs)**, which eliminates arbitrary error schemas across microservices.

Here is how a standardized 400 vs 422 looks in production:

#### Syntactic 400 Response (RFC 7807):
```http
HTTP/1.1 400 Bad Request
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/invalid-json",
  "title": "Invalid JSON Syntax",
  "status": 400,
  "detail": "Unexpected token ',' at line 3 column 14. Payload could not be parsed."
}
```

#### Semantic 422 Response (RFC 7807 with Field Extensions):
```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/problem+json

{
  "type": "https://api.example.com/errors/validation-failed",
  "title": "Unprocessable Entity",
  "status": 422,
  "detail": "The request payload failed domain validation checks.",
  "invalid_params": [
    {
      "name": "email",
      "reason": "Must be a valid email address with an active MX domain."
    },
    {
      "name": "age",
      "reason": "Age must be an integer between 18 and 120."
    },
    {
      "name": "subscription_plan",
      "reason": "Value must be one of: 'free', 'pro', 'enterprise'."
    }
  ]
}
```

## 4. Real Code — See It Working

### Example 1: Node.js / Express with Zod (2-Tier Pipeline)

This production Express setup demonstrates how Tier 1 body-parser errors produce `400` while Tier 2 Zod schema errors produce `422`.

```javascript
import express from "express";
import { z, ZodError } from "zod";

const app = express();

// 1. TIER 1: Built-in body parser middleware
// Limits payload size and parses raw JSON string into req.body
app.use(express.json({ limit: "100kb" }));

// 2. Custom error handler specifically for Tier 1 JSON parsing failures
app.use((err, req, res, next) => {
  // express.json() sets err.type === 'entity.parse.failed' on malformed JSON
  if (err instanceof SyntaxError && "body" in err) {
    return res.status(400).json({
      type: "https://api.example.com/errors/bad-request",
      title: "Bad Request",
      status: 400,
      detail: "Malformed JSON payload. Verify quotes, trailing commas, and brackets."
    });
  }
  next(err);
});

// Domain Schema Definition
const RegisterUserSchema = z.object({
  email: z.string().email("Invalid email format"),
  age: z.number().int().min(18, "Must be at least 18 years old"),
  password: z.string().min(8, "Password must be at least 8 characters long"),
  startDate: z.string().datetime(),
  endDate: z.string().datetime()
}).refine((data) => new Date(data.endDate) > new Date(data.startDate), {
  message: "End date must be chronologically after start date",
  path: ["endDate"] // Target specific field for frontend mapping
});

// 3. TIER 2: Validation Middleware
function validateBody(schema) {
  return (req, res, next) => {
    try {
      // Parse succeeds only if data matches types and domain refinements
      req.validatedBody = schema.parse(req.body);
      next();
    } catch (error) {
      if (error instanceof ZodError) {
        // Return 422 with structured field-level errors
        return res.status(422).json({
          type: "https://api.example.com/errors/validation-error",
          title: "Unprocessable Entity",
          status: 422,
          detail: "Validation failed for one or more fields.",
          invalid_params: error.errors.map((issue) => ({
            name: issue.path.join("."),
            reason: issue.message
          }))
        });
      }
      next(error);
    }
  };
}

// Controller route
app.post("/api/users/register", validateBody(RegisterUserSchema), (req, res) => {
  const { email, age } = req.validatedBody;
  res.status(201).json({
    message: "User registered successfully",
    user: { email, age }
  });
});
```

### Example 2: Python / FastAPI with Pydantic

FastAPI natively implements the 400 vs 422 separation out of the box using Pydantic.

```python
from datetime import datetime
from typing import Annotated
from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel, EmailStr, Field, model_validator

app = FastAPI()

class RegistrationPayload(BaseModel):
    email: EmailStr
    age: int = Field(..., ge=18, le=120, description="Age must be 18-120")
    password: str = Field(..., min_length=8)
    start_date: datetime
    end_date: datetime

    # Cross-field semantic validation
    @model_validator(mode="after")
    def verify_date_range(self) -> "RegistrationPayload":
        if self.end_date <= self.start_date:
            raise ValueError("end_date must be strictly after start_date")
        return self

# FastAPI automatically returns 422 for RequestValidationError (Pydantic schema failure)
# We customize the response shape to match RFC 7807 Problem Details
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    formatted_errors = [
        {
            "name": ".".join(str(loc) for loc in err["loc"] if loc != "body"),
            "reason": err["msg"]
        }
        for err in exc.errors()
    ]
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "type": "https://api.example.com/errors/validation-error",
            "title": "Unprocessable Entity",
            "status": 422,
            "detail": "Semantic validation failed for request payload.",
            "invalid_params": formatted_errors
        }
    )

@app.post("/api/users/register", status_code=status.HTTP_201_CREATED)
async def register_user(payload: RegistrationPayload):
    return {"message": "User registered", "email": payload.email}
```

### Example 3: Frontend Client Integration (React + React Hook Form + Axios)

Here is how a frontend client seamlessly routes a `400` to a global banner while mapping `422` directly to input fields:

```typescript
import React from "react";
import { useForm } from "react-hook-form";
import axios, { AxiosError } from "axios";

interface FormInputs {
  email: string;
  age: number;
  password: string;
}

interface RFC7807ValidationError {
  title: string;
  detail: string;
  invalid_params?: Array<{ name: keyof FormInputs; reason: string }>;
}

export function RegistrationForm() {
  const { register, handleSubmit, setError, formState: { errors } } = useForm<FormInputs>();
  const [globalBanner, setGlobalBanner] = React.useState<string | null>(null);

  const onSubmit = async (data: FormInputs) => {
    setGlobalBanner(null);
    try {
      await axios.post("/api/users/register", data);
      alert("Registration successful!");
    } catch (err) {
      const axiosError = err as AxiosError<RFC7807ValidationError>;
      const response = axiosError.response;

      if (!response) {
        setGlobalBanner("Network error. Please check your connection.");
        return;
      }

      // Branching by status code:
      if (response.status === 422 && response.data.invalid_params) {
        // TIER 2 ERROR: Map field-level validation errors to specific form inputs
        response.data.invalid_params.forEach((param) => {
          setError(param.name, {
            type: "server",
            message: param.reason
          });
        });
      } else if (response.status === 400) {
        // TIER 1 ERROR: Generic envelope/payload corruption
        setGlobalBanner("The request could not be processed by the server. Please refresh or contact support.");
      } else {
        setGlobalBanner(response.data.detail || "An unexpected error occurred.");
      }
    }
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)} className="space-y-4">
      {globalBanner && (
        <div className="p-3 bg-red-100 text-red-700 rounded">{globalBanner}</div>
      )}

      <div>
        <label>Email</label>
        <input {...register("email")} className="border p-2 w-full" />
        {errors.email && <span className="text-red-500 text-sm">{errors.email.message}</span>}
      </div>

      <div>
        <label>Age</label>
        <input type="number" {...register("age", { valueAsNumber: true })} className="border p-2 w-full" />
        {errors.age && <span className="text-red-500 text-sm">{errors.age.message}</span>}
      </div>

      <button type="submit" className="bg-blue-600 text-white px-4 py-2 rounded">
        Register
      </button>
    </form>
  );
}
```

## 5. The Interview Questions — All of Them, Done Properly

**Q: What is the core architectural difference between HTTP 400 and HTTP 422?**

HTTP 400 Bad Request indicates a **syntactic, structural, or transport-level failure**. The server cannot parse the incoming request envelope—examples include malformed JSON syntax, invalid character encodings, unparseable query strings, or mismatched content-length headers. The server cannot even convert the raw byte stream into an internal domain object.

HTTP 422 Unprocessable Entity indicates a **semantic, logical, or business-rule failure**. The request was parsed perfectly into an internal domain object, the Content-Type is valid, and the JSON syntax is flawless. However, the data values violate domain constraints—such as an invalid email format, a negative price, an end date prior to a start date, or a non-existent foreign key reference.

---

**Q: If a client sends valid JSON like `{"email": "invalid-email", "age": -10}`, why is returning 422 better than 400?**

Returning 422 establishes a clear contract with API consumers and frontend clients:
1. **Frontend ergonomics:** Client libraries (like React Hook Form or Formik) and mobile clients can inspect the status code. If it's a 422, they immediately parse the `invalid_params` or `errors` array to display red highlights and inline error messages under each input field.
2. **Monitoring & Sentry alerts:** A sudden spike in 400 errors usually indicates a frontend bug (such as an improper JSON serialization function or a breaking API contract). A spike in 422 errors simply reflects normal user behavior (users entering invalid form inputs). Bundling both into 400 corrupts engineering observability.
3. **Automated SDK retry logic:** SDKs know that a 400 error implies a transport or serialization failure that should not be retried with the same payload structure, whereas a 422 informs an automated client which specific domain parameters must be altered.

---

**Q: Should duplicate entity errors (like "Email already registered") return 400, 409 Conflict, or 422?**

In strict REST theory, **409 Conflict** is designed for state conflicts with the target resource's current state on the server (such as an optimistic locking version mismatch or a unique constraint violation against the database). 

However, in modern API design:
- If the endpoint is a user registration form, many modern engineering teams return **422 Unprocessable Entity** with `{ "invalid_params": [{ "name": "email", "reason": "Email is already in use." }] }` so that the client form handler highlights the email input identically to other validation failures.
- If the endpoint is a distributed state management or file synchronization API (e.g., Git push conflicts, concurrent document edits, WebDAV lock conflicts), **409 Conflict** is the standard.
- **400 Bad Request** is the wrong status code in both cases because the request syntax was not malformed.

---

**Q: What HTTP status code should be returned if the client sends a valid JSON payload with `Content-Type: text/plain`?**

The server should return **`415 Unsupported Media Type`**, not 400 or 422. 

The client sent a valid body, but informed the server that the media type is `text/plain`. The server does not accept plain text for this endpoint. If the client sent `Content-Type: application/json` but the body contained raw plain text that failed JSON parsing, the server would return `400 Bad Request`.

---

**Q: How should a client-side HTTP interceptor (e.g., Axios or TanStack Query) handle 400 vs 422 errors?**

In a production frontend architecture:
- **Global Interceptor on 400:** A 400 error bypasses field-level form logic. The interceptor logs the failure to an observability tool (like Sentry or Datadog) because it suggests a client-side serialization bug, and displays a general alert banner ("We could not submit your request due to an unexpected format error").
- **Local Form Handler on 422:** A 422 error is intercepted and passed directly to the active form state manager (e.g., React Hook Form's `setError`). The global toast is suppressed so the user is not overwhelmed, and the individual fields on screen receive red borders and contextual validation messages.

## 6. The Traps — What Goes Wrong

### Trap 1: Returning 422 on Malformed JSON (Parser Failure)

- **The Wrong Assumption:** A developer wraps their entire route handler in a `try/catch` and maps every caught error to `res.status(422)`.
- **Why It's Wrong:** When the client sends `{"name": "Alice",}` (malformed JSON with a trailing comma), `JSON.parse` throws a `SyntaxError`. There is no "entity" or structured object for the server to validate.
- **What Happens:** The server returns 422 with a message like `"Validation failed: undefined"`. The frontend assumes valid fields were checked and tries to look for field names that don't exist.
- **The Fix:** Handle body-parsing errors in Tier 1 middleware and return `400 Bad Request`. Only return `422` after JSON parsing has succeeded and schema validation has run.

---

### Trap 2: The "HTTP 200 with `{ success: false }`" Anti-Pattern

- **The Wrong Assumption:** Returning `200 OK` with `{ success: false, errors: { email: "Invalid" } }` so the frontend network call doesn't "throw" an exception.
- **Why It's Wrong:** This completely destroys standard HTTP semantics:
  1. API Gateways and CDNs treat the response as a successful request and may cache the error.
  2. Frontend HTTP clients (`fetch`, `axios`, `react-query`) evaluate `response.ok` as true and route the failure to their success handlers.
  3. Load balancers and synthetic monitors record a 100% health check success rate even when every single user submission is failing validation.
- **The Fix:** Always return standard HTTP error status codes (400 for syntax, 422 for validation). Let the client's rejection handlers do their job.

---

### Trap 3: Returning 400 with Plain Strings, Forcing String-Sniffing on Frontend

- **The Wrong Assumption:** Returning `400 Bad Request` with `{ message: "Invalid email and password must be 8 chars" }`.
- **Why It's Wrong:** The frontend has to write brittle regular expressions or string searches against the error message: `if (err.message.includes("email"))`. If a backend engineer refactors the string to `"Email address is not formatted properly"`, the frontend's regex silently breaks.
- **The Fix:** Return `422` with machine-readable field paths matching your schema (`invalid_params: [{ name: "email", reason: "..." }]`).

---

### Trap 4: Leaking Internal Database and ORM Exceptions in 422 Payloads

- **The Wrong Assumption:** Catching a database constraint error and dumping the raw error into the 422 response body:
  ```json
  { "error": "SequelizeUniqueConstraintError: duplicate key value violates unique constraint 'users_email_key'" }
  ```
- **Why It's Wrong:** This is an Information Disclosure vulnerability (OWASP Top 10). It exposes your database technology (PostgreSQL, MySQL), ORM internals, table names, and constraint names to potential attackers.
- **The Fix:** Sanitize database exceptions in an error-formatting layer and translate them into friendly, domain-safe messages before responding.

## 7. Compare With Related Concepts

| Status Code | Layer Where It Fails | Why It Fails | Example Scenario |
| :--- | :--- | :--- | :--- |
| **400 Bad Request** | Transport / Syntactic Parser | The server cannot parse or decode the request envelope. | Malformed JSON `{"a": 1,}`, unescaped URL query string, corrupted HTTP headers. |
| **422 Unprocessable Entity** | Application / Domain Schema | The request envelope is parsed, but field values violate business rules. | `age: -5`, `end_date < start_date`, invalid email regex format. |
| **409 Conflict** | State / Concurrency | The payload is valid, but applying it conflicts with the current database state. | Optimistic lock collision (version mismatch), editing an already deleted resource. |
| **415 Unsupported Media Type** | Content Negotiation | The server refuses the format specified by the `Content-Type` header. | Sending `Content-Type: application/xml` to a JSON-only endpoint. |
| **404 Not Found** | Routing / Resource Identification | The endpoint URI path does not point to an existing resource. | `GET /api/v1/non-existent-route` |

### Rules of Thumb:
- Use **400** when the server **cannot read the data structure** (broken JSON, broken headers, corrupted framing).
- Use **422** when the server **read the data structure fine, but refuses what it says** (bad input values, invalid business logic).
- Use **409** when the request is valid, but the **server's current state forbids the change** (version conflict, concurrent edit).
- Use **415** when the server **does not support the payload's Content-Type**.
