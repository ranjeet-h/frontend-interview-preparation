# 401 Unauthorized vs 403 Forbidden: Authentication vs Authorization

## 1. Why This Exists — The Problem First

Picture this production incident: A user with a standard "Viewer" role clicks on the "Billing Settings" tab in your SaaS application. The backend endpoint `/api/billing` checks their role, sees they are not an "Admin", and responds with an HTTP status code.

If your backend developer lazily returns a `401 Unauthorized`, your frontend's global HTTP interceptor springs into action. The interceptor sees `401`, assumes the user's session has expired, wipes the user's access token from memory and `localStorage`, and forcibly redirects them to `/login`. The user enters their email and password, logs back in successfully, and gets redirected right back to their previous page—which immediately calls `/api/billing`, receives another `401`, wipes their credentials again, and kicks them back to `/login`. Your user is now trapped in an infinite login loop.

Now consider the reverse failure: a user leaves their tab open overnight. The next morning, their JWT access token has expired. They click "Save Changes". The backend inspects the expired signature and returns a `403 Forbidden`. The frontend interceptor sees `403`, treats it as a permanent permission denial, displays a red toast saying "You do not have permission to perform this action," and suppresses the silent token-refresh flow. The user is left staring at a broken UI, unable to save their work, despite having a perfectly valid refresh token ready to renew their session.

These bugs happen because developers treat `401` and `403` as interchangeable "security error" codes. They represent two fundamentally different phases of security: **Authentication** (verifying identity) and **Authorization** (evaluating permissions).

## 3. How It Actually Works — The Full Explanation

### The Core Distinction: Authentication vs Authorization

Every protected backend request passes through two distinct evaluation gates in strict sequential order:

```
Incoming Request
      │
      ▼
┌──────────────────────────────────────┐
│ Gate 1: Authentication Middleware    │ ──(Fails)──► HTTP 401 Unauthorized
│ "Who are you?" (Verify Credentials)  │              (Include WWW-Authenticate header)
└──────────────────────────────────────┘
      │ (Passes: req.user is attached)
      ▼
┌──────────────────────────────────────┐
│ Gate 2: Authorization Middleware     │ ──(Fails)──► HTTP 403 Forbidden
│ "What are you allowed to do?" (RBAC) │              (Identity confirmed, access denied)
└──────────────────────────────────────┘
      │ (Passes: permissions verified)
      ▼
┌──────────────────────────────────────┐
│ Controller / Business Logic Handler  │ ──► HTTP 200 / 201 / etc.
└──────────────────────────────────────┘
```

### 1. HTTP 401 Unauthorized (Actually "Unauthenticated")

The HTTP status code name `401 Unauthorized` is historically inaccurate. In RFC 9110 (and earlier RFC 7235), `401` means **Unauthenticated**.

- **What triggers it:** The request is missing credentials, the authorization header is malformed, the session cookie is missing, the JWT signature is invalid, or the token has expired.
- **The Server State:** The server has no confirmed identity for the requester. `req.user` is `null` or `undefined`.
- **The RFC Requirement:** Per RFC 9110 Section 15.5.2, whenever a server returns a `401`, it **MUST** send a `WWW-Authenticate` response header indicating what authentication scheme is supported (e.g., `WWW-Authenticate: Bearer realm="Access to API", error="invalid_token"`).
- **Frontend Reaction:** The frontend should attempt a silent token refresh (using a refresh token or refresh cookie). If refresh fails or no refresh mechanism exists, it clears stored session state and redirects the user to the login screen.

### 2. HTTP 403 Forbidden

`403 Forbidden` means the server successfully authenticated the user, verified their identity, but refuses to authorize the specific action requested.

- **What triggers it:** Role-Based Access Control (RBAC) failure (e.g., a member trying to delete a workspace), Attribute-Based Access Control (ABAC) failure, tenant isolation mismatch, IP whitelist rejection, or CORS origin rejection.
- **The Server State:** The server knows exactly who the user is. `req.user` is populated (e.g., `user_id: "usr_987"`).
- **The RFC Requirement:** Unlike `401`, re-authenticating with the same credentials will make no difference. The server SHOULD explain why access was forbidden in the response body unless security considerations dictate silence.
- **Frontend Reaction:** The frontend MUST NOT redirect to login. It should display an "Access Denied" view, disable the restricted button, or prompt the user to upgrade their subscription plan.

### 3. The Security Dilemma: When to Return 404 Instead of 403

Returning `403 Forbidden` explicitly confirms that a resource exists at that URL. This creates a critical security vulnerability known as **Resource Enumeration** and **Insecure Direct Object Reference (IDOR) probing**.

Imagine an attacker brute-forcing URLs on your multi-tenant platform:
- `GET /api/v1/invoices/1001` -> returns `200 OK` (their own invoice)
- `GET /api/v1/invoices/1002` -> returns `403 Forbidden`
- `GET /api/v1/invoices/1003` -> returns `404 Not Found`

By returning `403`, the API reveals that invoice `1002` exists and belongs to another customer, while `1003` does not exist. The attacker now knows valid invoice IDs to target with other exploits.

**The Golden Rule for Multi-Tenant Security:**
If a user tries to access a private resource belonging to another tenant or private organization, return **`404 Not Found`**, not `403 Forbidden`. This is the exact pattern used by platforms like GitHub: accessing a private repository you don't belong to returns `404`, making it impossible for outsiders to determine whether a private repository even exists.

Use `403 Forbidden` when the resource is publicly known, but the authenticated user lacks permission for the specific action (e.g., a standard user trying to `POST /api/v1/projects/alpha/settings` when they are already a member of project `alpha`).

## 4. Real Code — See It Working

### Backend: Clean Separation of 401 and 403 Middleware (Express & TypeScript)

Here is production-grade middleware separating identity verification from permission enforcement:

```typescript
import { Request, Response, NextFunction } from 'express';
import jwt from 'jsonwebtoken';

// Extend Express Request to carry the authenticated user payload
export interface AuthenticatedUser {
  id: string;
  email: string;
  role: 'viewer' | 'editor' | 'admin';
  tenantId: string;
}

export interface AuthenticatedRequest extends Request {
  user?: AuthenticatedUser;
}

/**
 * Gate 1: Authentication Middleware
 * Validates credentials. Returns 401 if missing, expired, or invalid.
 */
export function authenticateToken(
  req: AuthenticatedRequest,
  res: Response,
  next: NextFunction
): void {
  const authHeader = req.headers['authorization'];
  // Authorization header format: "Bearer <token>"
  const token = authHeader && authHeader.startsWith('Bearer ') 
    ? authHeader.split(' ')[1] 
    : null;

  if (!token) {
    // RFC 9110 requires WWW-Authenticate header on 401 responses
    res.setHeader('WWW-Authenticate', 'Bearer realm="api", error="missing_token"');
    res.status(401).json({
      error: 'unauthorized',
      message: 'Authentication token is required to access this endpoint.'
    });
    return;
  }

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET as string) as AuthenticatedUser;
    // Attach verified identity to request context
    req.user = decoded;
    next();
  } catch (err: any) {
    // Distinguish expired tokens from tampered tokens for observability
    const isExpired = err.name === 'TokenExpiredError';
    
    res.setHeader(
      'WWW-Authenticate',
      `Bearer realm="api", error="${isExpired ? 'token_expired' : 'invalid_token'}"`
    );
    res.status(401).json({
      error: 'unauthorized',
      message: isExpired ? 'Token has expired.' : 'Token signature is invalid.'
    });
  }
}

/**
 * Gate 2: Authorization Middleware (Role-Based Access Control)
 * Runs AFTER authentication. Returns 403 if user lacks required role.
 */
export function requireRoles(...allowedRoles: Array<'viewer' | 'editor' | 'admin'>) {
  return (req: AuthenticatedRequest, res: Response, next: NextFunction): void => {
    // Guard against programming errors where auth was accidentally omitted
    if (!req.user) {
      res.status(500).json({ error: 'server_error', message: 'Auth middleware missing.' });
      return;
    }

    if (!allowedRoles.includes(req.user.role)) {
      // 403: User is known, but does not have permission for this route
      res.status(403).json({
        error: 'forbidden',
        message: `Role '${req.user.role}' is not permitted to perform this operation. Required: ${allowedRoles.join(', ')}.`
      });
      return;
    }

    next();
  };
}

/**
 * Gate 3: Object-Level Authorization (IDOR Prevention)
 * Returns 404 instead of 403 to avoid leaking existence across tenants.
 */
export async function requireDocumentAccess(
  req: AuthenticatedRequest,
  res: Response,
  next: NextFunction
): Promise<void> {
  const documentId = req.params.docId;
  const user = req.user!;

  // Simulated database lookup
  const document = await findDocumentById(documentId);

  if (!document) {
    res.status(404).json({ error: 'not_found', message: 'Document not found.' });
    return;
  }

  // Security pattern: If document belongs to another tenant, return 404, NOT 403
  if (document.tenantId !== user.tenantId) {
    res.status(404).json({ error: 'not_found', message: 'Document not found.' });
    return;
  }

  next();
}

// Dummy database helper for illustration
async function findDocumentById(id: string) {
  return id === 'doc_123' ? { id: 'doc_123', tenantId: 'tenant_abc' } : null;
}
```

### Frontend: Resilient Axios Interceptor Handling 401 vs 403

Here is how a senior frontend client architecture separates the two responses:

```typescript
import axios, { AxiosError, InternalAxiosRequestConfig } from 'axios';

const apiClient = axios.create({
  baseURL: 'https://api.example.com/v1',
});

let isRefreshing = false;
let failedQueue: Array<{
  resolve: (token: string) => void;
  reject: (error: any) => void;
}> = [];

function processQueue(error: any, token: string | null = null) {
  failedQueue.forEach((promise) => {
    if (error) {
      promise.reject(error);
    } else if (token) {
      promise.resolve(token);
    }
  });
  failedQueue = [];
}

apiClient.interceptors.response.use(
  (response) => response,
  async (error: AxiosError) => {
    const originalRequest = error.config as InternalAxiosRequestConfig & { _retry?: boolean };

    // Scenario A: 401 Unauthorized (Identity problem -> Refresh token or Login)
    if (error.response?.status === 401 && !originalRequest._retry) {
      // Don't retry if the 401 came from the refresh endpoint itself
      if (originalRequest.url?.includes('/auth/refresh')) {
        // Refresh token itself expired -> force logout
        localStorage.removeItem('access_token');
        window.location.href = '/login?reason=session_expired';
        return Promise.reject(error);
      }

      if (isRefreshing) {
        // Queue concurrent requests while a single refresh call is in flight
        return new Promise((resolve, reject) => {
          failedQueue.push({ resolve, reject });
        })
          .then((newToken) => {
            originalRequest.headers.Authorization = `Bearer ${newToken}`;
            return apiClient(originalRequest);
          })
          .catch((err) => Promise.reject(err));
      }

      originalRequest._retry = true;
      isRefreshing = true;

      try {
        // Request new access token using httpOnly refresh cookie
        const { data } = await axios.post('https://api.example.com/v1/auth/refresh', {}, {
          withCredentials: true,
        });

        const newAccessToken = data.accessToken;
        localStorage.setItem('access_token', newAccessToken);

        // Update default header and replay queued requests
        apiClient.defaults.headers.common.Authorization = `Bearer ${newAccessToken}`;
        processQueue(null, newAccessToken);

        // Replay the original failed request
        originalRequest.headers.Authorization = `Bearer ${newAccessToken}`;
        return apiClient(originalRequest);
      } catch (refreshError) {
        processQueue(refreshError, null);
        localStorage.removeItem('access_token');
        window.location.href = '/login?reason=session_expired';
        return Promise.reject(refreshError);
      } finally {
        isRefreshing = false;
      }
    }

    // Scenario B: 403 Forbidden (Permission problem -> Show UI banner, NEVER logout)
    if (error.response?.status === 403) {
      console.warn('Access denied: User lacks sufficient permissions.');
      // Notify application UI without touching auth state
      window.dispatchEvent(
        new CustomEvent('app:permission-denied', {
          detail: {
            message: (error.response.data as any)?.message || 'Access Denied',
          },
        })
      );
      return Promise.reject(error);
    }

    return Promise.reject(error);
  }
);

export default apiClient;
```

## 5. The Interview Questions — All of Them, Done Properly

**Q: What is the fundamental difference between HTTP 401 Unauthorized and HTTP 403 Forbidden?**

401 Unauthorized means the request lacks valid authentication credentials. The client is anonymous, unverified, or has supplied an expired/tampered token. The server is asking: *"Who are you?"* The client can resolve a 401 by supplying valid credentials (such as logging in or refreshing a token).

403 Forbidden means the client's identity has been successfully authenticated, but the verified user is not authorized to perform the requested action on that resource. The server knows who the user is, but replies: *"You do not have permission."* Re-authenticating with the same user credentials will never change the outcome.

---

**Q: Why is 401 called "Unauthorized" when it actually represents an authentication failure?**

This is an acknowledged historical naming misnomer from the early HTTP/1.0 specification written in the 1990s. The authors used "Unauthorized" to mean "unauthenticated".

The HTTP specification (RFC 9110, Section 15.5.2) explicitly clarifies that `401 Unauthorized` must be used when authentication is required and has failed or has not yet been provided. Furthermore, RFC 9110 mandates that a `401` response **MUST** include a `WWW-Authenticate` header containing at least one challenge applicable to the target resource. In contrast, `403 Forbidden` is the true authorization error code.

---

**Q: How should a frontend Single Page Application (SPA) handle 401 vs 403 responses differently?**

A frontend application must treat 401 and 403 through completely separate control flows:
1. **On 401:** The frontend enters an authentication recovery flow. If using short-lived access tokens, it pauses pending outgoing requests and fires a refresh token request. If refresh succeeds, it replays the failed request with the new token. If refresh fails, it purges local session storage and redirects the user to the login route, preserving the return URL.
2. **On 403:** The frontend must **never** clear authentication tokens and must **never** redirect to the login page. Doing so causes infinite redirect loops. Instead, it surfaces an inline error, a toast notification ("You lack permission to edit this workspace"), or redirects to an "Upgrade Plan" / "Access Denied" page while keeping the user logged in.

---

**Q: When should an API return 404 Not Found instead of 403 Forbidden for a protected resource?**

An API should return `404 Not Found` instead of `403 Forbidden` whenever revealing the existence of a resource poses a security risk or leaks sensitive business information.

In multi-tenant SaaS systems, if User A from Company X tries to fetch `/api/invoices/999` which belongs to Company Y, returning `403` confirms that invoice 999 exists and belongs to a competitor. Returning `404` conceals whether the resource exists at all. This prevents Insecure Direct Object Reference (IDOR) scanning and object ID enumeration. GitHub implements this standard: unauthorized requests to private repositories always return `404`.

---

**Q: Can an authenticated request with a valid token ever receive a 401, or is 401 strictly for unauthenticated users?**

An authenticated request can receive a `401` if the credentials were valid when generated but have become invalid by the time the request hits the server. This happens when:
1. The token's expiration timestamp (`exp` claim) has passed.
2. The user changed their password or revoked active sessions on another device, causing the server-side token version or session blacklist to invalidate the token.
3. The server rotated its signing keys, making the token's cryptographic signature unverifiable.
4. The client sent credentials intended for a different audience (`aud` claim) or issuer (`iss` claim).

In all these cases, the server cannot trust the identity, so it returns `401` to force re-authentication.

---

**Q: What is the `WWW-Authenticate` header, and why does it matter for 401 responses?**

The `WWW-Authenticate` response header is a mandatory HTTP header that a server must include whenever returning a `401 Unauthorized` status code. It tells the client how it is expected to authenticate.

For example:
- `WWW-Authenticate: Basic realm="Secure Area"` (tells the client to send standard HTTP Basic Auth headers).
- `WWW-Authenticate: Bearer realm="API", error="invalid_token", error_description="The access token expired"` (tells an OAuth2/OIDC client that a Bearer token is needed and why the previous one was rejected).

Standard HTTP clients, browsers, and API gateways rely on this header to negotiate authentication schemes automatically without hardcoding assumptions.

## 6. The Traps — What Goes Wrong

### Trap 1: The Infinite Login Redirect Loop
- **The Wrong Assumption:** "401 means permission denied, so I'll return 401 when a regular member tries to access the admin dashboard."
- **Why It's Wrong:** The frontend's global interceptor is programmed to catch 401, clear tokens, and redirect to `/login`.
- **What Actually Happens:** The user logs in -> gets redirected to the admin dashboard -> backend returns 401 -> frontend wipes token -> user gets redirected to `/login`. The user is stuck in a loop forever.
- **The Fix:** Return `403 Forbidden` for permission failures. Only return `401` when identity is unknown or invalid.

---

### Trap 2: The Stale Session Deadlock
- **The Wrong Assumption:** "The token expired, but this is a protected route, so I'll return 403 Forbidden."
- **Why It's Wrong:** The client treats 403 as a business logic rejection, not an expired credential.
- **What Actually Happens:** The client displays a permanent "Access Denied" error message. The user cannot fix it by clicking around because the frontend never triggers the token refresh flow. The user is trapped until they manually clear their browser cookies or click a hard "Log Out" button.
- **The Fix:** An expired token must ALWAYS return `401 Unauthorized` with `error="token_expired"` in the `WWW-Authenticate` header.

---

### Trap 3: Information Leakage via 403 (Resource Enumeration)
- **The Wrong Assumption:** "Returning 403 is more accurate than 404 because the resource actually does exist in the database."
- **Why It's Wrong:** Accuracy to internal database state should never override security boundary isolation.
- **What Actually Happens:** An attacker scripts requests across `/api/organizations/1` through `/api/organizations/10000`. Status `404` means unallocated; status `403` means an active enterprise customer exists with that ID. The attacker builds an exact map of your customer IDs and organization sizes.
- **The Fix:** If the requesting user does not have permission to know that an object exists, return `404 Not Found`.

---

### Trap 4: Omission of the `WWW-Authenticate` Header
- **The Wrong Assumption:** "Returning `{ status: 401, error: 'Unauthorized' }` as a JSON body is sufficient."
- **Why It's Wrong:** RFC 9110 strictly mandates the `WWW-Authenticate` header on all 401 responses.
- **What Actually Happens:** API gateways, mobile SDKs, automated testing suites, and OpenAPI validators fail or throw protocol validation errors because the HTTP contract is violated.
- **The Fix:** Always set `res.setHeader('WWW-Authenticate', 'Bearer ...')` when returning a 401.

---

### Trap 5: Catch-All Global 4xx Interceptors
- **The Wrong Assumption:** "I'll create a single Axios interceptor that catches any error response with status `>= 400` and redirects to an error page."
- **Why It's Wrong:** 4xx errors represent completely distinct categories: `400` (bad payload), `401` (re-authenticate), `403` (permission denied), `404` (not found), and `422` (form validation failure).
- **What Actually Happens:** A simple form validation error (422) or route not found (404) kicks the user out of the application or redirects them to the wrong screen.
- **The Fix:** Write granular status-code branches in your client interceptor.

## 7. Compare With Related Concepts

| Status Code | Primary Meaning | Typical Cause | Required Client Action |
| :--- | :--- | :--- | :--- |
| **401 Unauthorized** | **Unauthenticated** (Identity unknown) | Missing, invalid, or expired token | Refresh token or redirect to `/login` |
| **403 Forbidden** | **Unauthorized** (Identity verified, access denied) | Insufficient RBAC role, wrong tenant, IP block | Display "Access Denied" or prompt tier upgrade |
| **404 Not Found** | **Non-existent or Concealed** | URL does not exist OR hidden for security | Show 404 page; do not retry |
| **419 / 440** | **Session Timeout** (Non-standard) | Laravel CSRF expiry (419) or IIS timeout (440) | Refresh CSRF token or prompt re-login |
| **429 Too Many Requests** | **Rate Limited** | Request quota or burst limit exceeded | Back off and retry after `Retry-After` seconds |
| **451 Unavailable For Legal Reasons** | **Legally Censored / Blocked** | Court order, GDPR/geo-restriction, DMCA | Display legal takedown notice |
