# 401 vs 403

## Detailed explanation

401 means the request is unauthenticated or has invalid credentials; 403 means the user is authenticated but not allowed to perform the action.

## 1. One-line mental model

401 asks who you are; 403 says you are known but not allowed.

## 2. Problem it solves

Auth bugs become confusing when APIs return 403 for missing login or 401 for permission failure.

## 3. Core idea

- Return 401 when token/cookie is missing, expired, or invalid.
- Return 403 when identity is valid but role/permission is insufficient.
- 401 can trigger login or refresh-token flow.
- 403 should show access denied, not silently refresh forever.
- Never expose sensitive permission details in the error body.

## 4. Visual / analogy

```txt
401 = no valid badge. 403 = valid badge, wrong room.
```

## 5. Minimal example

```txt
if (!user) return res.sendStatus(401); if (!user.isAdmin) return res.sendStatus(403);
```

## 6. Real-world example

Admin endpoint: no token returns 401; logged-in normal user returns 403.

## 7. Common interview questions

#### What is the difference between 401 and 403?
- **The Engine Mechanism (Why it behaves this way):** 401 Unauthorized means the request lacks valid authentication credentials — the server doesn't know who the user is because the token is missing, expired, or invalid. 403 Forbidden means the server knows who the user is (authentication succeeded) but the user lacks permission to perform the requested action — the identity is valid but the role or permission check failed. The backend middleware determines this: auth middleware returns 401 when identity verification fails; authorization middleware returns 403 when permission checks fail.
- **The Unforgettable Mental Model:** 401 is **"Show me your ID"** — you don't have one or it's expired. 403 is **"Nice ID, but you're not on the guest list."**
- **The Trap:** Returning 403 when the user isn't logged in. This confuses the frontend — it should redirect to login on 401, but 403 makes it think the user is logged in but lacks permission.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: 401 means the request is unauthenticated — the server doesn't know who you are because credentials are missing, expired, or invalid. 403 means you're authenticated but not authorized — the server knows your identity but you lack the required role or permission. 401 should trigger a login or token refresh flow; 403 should show an access denied message. The distinction matters because the frontend handles them differently."

#### Why does the 401 vs 403 distinction matter?
- **The Engine Mechanism (Why it behaves this way):** The distinction drives different client behavior. On 401, the frontend redirects to login or attempts token refresh. On 403, the frontend shows an access denied page — redirecting to login would create an infinite loop since the user is already authenticated. Security-wise, returning 401 for permission failures leaks information (confirming the resource exists), while returning 403 for unauthenticated requests leaves the client in a confused state about whether login would help.
- **The Unforgettable Mental Model:** 401 and 403 are **different emergency protocols**. 401 = "evacuate and re-enter with proper credentials." 403 = "stay put, you're in the building but not allowed in this room."
- **The Trap:** Returning 404 instead of 403 to hide resource existence. While this is a valid security pattern for sensitive resources, it should be a deliberate choice, not a default. Overusing it makes debugging impossible.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: The distinction matters because it drives different client behavior. 401 triggers authentication flows — login redirects or token refreshes. 403 triggers authorization UI — access denied messages. If you return 403 for unauthenticated requests, the frontend may try to refresh a token that doesn't exist, creating an infinite loop. If you return 401 for permission failures, the frontend redirects to login even though the user is already authenticated. Getting this right ensures the user sees the right action to take."

#### What bugs happen when 401 and 403 are confused?
- **The Engine Mechanism (Why it behaves this way):** Returning 403 for missing auth causes the frontend to show "access denied" instead of prompting login — the user thinks they're blocked when they just need to sign in. Returning 401 for permission failures causes infinite login loops — the user logs in, gets redirected back to login because the API returns 401 for the protected resource. Both bugs create poor UX and make debugging difficult because the status code doesn't match the actual problem.
- **The Unforgettable Mental Model:** Confusing 401 and 403 is like **giving the wrong directions**. Telling someone "you need a ticket" when they're already in the building (401 instead of 403), or telling them "you're in the wrong building" when they just need to show ID (403 instead of 401).
- **The Trap:** Using 403 for both scenarios to "be safe." This is the most common mistake — it's easier to return 403 for everything auth-related, but it breaks the frontend's error handling logic.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: Confusing 401 and 403 causes two common bugs. Returning 403 for unauthenticated requests shows 'access denied' to users who just need to log in — they think they're blocked when they're not logged in. Returning 401 for permission failures causes infinite login loops — the user authenticates, but the API still returns 401 for the protected resource, redirecting them back to login. The fix is clear: auth middleware returns 401 for identity failures, authorization middleware returns 403 for permission failures."

#### How does a frontend client react differently to 401 vs 403?
- **The Engine Mechanism (Why it behaves this way):** On 401, the frontend typically attempts token refresh first (if using refresh tokens), then redirects to a login page if refresh fails. The client may also clear stored tokens and reset application state. On 403, the frontend shows an access denied page or disables the UI element that triggered the request. It does NOT attempt token refresh or redirect to login because the user is already authenticated — the issue is permissions, not identity.
- **The Unforgettable Mental Model:** 401 response = **front desk says "please get a badge."** 403 response = **front desk says "your badge doesn't grant access to this floor."**
- **The Trap:** Having the frontend treat all 4xx errors the same way. A unified error handler that redirects to login for every 4xx will incorrectly redirect on 403, 404, and 422.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: On 401, the frontend attempts token refresh and redirects to login if refresh fails. It may also clear stored tokens and reset state. On 403, the frontend shows an access denied message or disables the relevant UI — it does not redirect to login because the user is already authenticated. The key difference: 401 means 'prove who you are,' so the client re-authenticates. 403 means 'you can't do this,' so the client informs the user and moves on."

#### How would you test 401 and 403 behavior?
- **The Engine Mechanism (Why it behaves this way):** Testing 401 involves sending requests without credentials, with expired tokens, and with invalid tokens — all should return 401. Testing 403 involves sending requests with valid credentials but insufficient permissions — a regular user accessing admin endpoints should return 403. Integration tests verify that auth middleware correctly distinguishes between "no identity" and "insufficient permissions." E2E tests verify the frontend redirects on 401 and shows access denied on 403.
- **The Unforgettable Mental Model:** Testing 401/403 is like **testing a building's security**. Test 1: no badge (401). Test 2: expired badge (401). Test 3: valid badge but wrong floor (403). Test 4: valid badge and correct floor (200).
- **The Trap:** Only testing with admin credentials. If all tests use admin tokens, you never verify that regular users get 403 on admin endpoints — a critical security gap.
- **Senior Interview Playbook (Verbal Script):** "When asked this in an interview, say: I test 401 by sending requests without tokens, with expired tokens, and with invalid tokens — all should return 401. I test 403 by sending requests with valid but underprivileged tokens to protected endpoints — a regular user hitting an admin route should return 403. I also test the happy path with proper credentials to ensure 200. For E2E, I verify the frontend redirects to login on 401 and shows access denied on 403. I always test with multiple user roles to catch permission gaps."

## 8. Active recall test

1. **Explain the difference between 401 and 403.**
   - **Explanation:** 401 means unauthenticated — the server doesn't know who you are (missing, expired, or invalid credentials). 403 means authenticated but not authorized — the server knows your identity but you lack the required permission or role.

2. **Give one production bug from confusing 401 and 403.**
   - **Explanation:** Returning 401 for permission failures causes infinite login loops. The user logs in successfully, but the API returns 401 for the protected resource, triggering another login redirect. The user is trapped in a login cycle even though they're authenticated.

3. **Give one API example where the distinction matters.**
   - **Explanation:** An admin endpoint `GET /admin/users`: no token returns 401 (redirect to login); valid token from a regular user returns 403 (show access denied). The frontend handles each differently — login flow vs. permission denial.

4. **Explain how a frontend client should react to 401 vs 403.**
   - **Explanation:** On 401: attempt token refresh, then redirect to login if refresh fails. On 403: show an access denied message or disable the UI element. Do NOT redirect to login on 403 since the user is already authenticated.
